# Approval and connector persistence proposal v1 — separate review required

Status: NOT INSTALLED. Production HOLD / NO-GO. No migration number is allocated. No certified migration, schema, trigger, runner or backup/restore inventory is changed. Reconcile numbering with independently reviewed migration 010 and quota proposals before preparing DDL.

## Decision and supported boundary

The blueprint sections 22–25, 28, 32, 38–43 and 49–51 require tenant/website isolation, explicit approval, capability-scoped connections, revocation, audit and fail-closed controls. The existing internal approval queue is deliberately not a publication authorization. A prior `growth_approval_decisions.decision='approved'` or caller `approvalVerified=true` is never translated into publish permission.

The v1 bridge accepts a separately recorded explicit **content_publication** authorization. It binds organization, website, scheduled content ID/version and canonical full-record SHA-256, channel, destination ID/revision/target, completed reservation ID, durable content approval event ID, approver, approval/issuance/expiry time and current policy hash. The approval event must actually exist in `growth_content_events` with kind `approve`, matching actor, timestamp and preceding approved-version snapshot. Reconstructing the scheduled record from that snapshot must produce the current fingerprint. Changes to draft, rights/quality, sources, version, schedule or scope require new review. Content version includes scheduling; the authorization is created after the exact schedule/destination has been explicitly reviewed. No scheduling worker is started.

Both requester and original approver must currently be enabled owner/admin members of that organization. Editor may prepare/approve a draft under the existing lifecycle but cannot authorize this publication bridge; viewer and unknown roles deny. The database read rechecks session expiry/revocation and enabled user, rather than trusting a cached HTTP role. Memberships are organization-wide in the certified schema; independent website-specific ACLs remain a separate extension, not an implemented entitlement.

Authorization validity is at most 24 hours from issuance, with current membership/policy checks on every new claim. Connector evidence validity is at most five minutes. Immediately before consuming the authorization, verify that server time is still within the minimum session/approval/connector expiry; a deadline crossed inside the transaction rolls back the claim. Changing policy revision or destination revision invalidates old approvals even if booleans later return to the same values. Policy writers must update revisions for semantic changes, not silently re-enable an old revision.

Use InnoDB, the exact certified parent charset/collation for CHAR(36) organization/website/user/reservation columns, and bounded binary/case-sensitive identifiers consistent with the proposed content tables. All composite index widths, page size, row format, FK dependencies and DDL must receive independent MariaDB review.

Do not alter the certified 15/20-table or migration-ledger/trigger/FK inventory checks to accept a new schema. ## Issuance, trust and transaction contract

No authorization issuance endpoint or automatic approval writer is connected. Before implementing one, require an authenticated bounded-JSON/strict-Origin request with server-derived org/site context, current owner/admin consent to the exact content version, schedule, destination and policy, and the durable content approval event. Insert the complete authorization atomically with an immutable issuance audit; never fill missing fields from an internal recommendation approval. Revocation must be an authenticated, audited one-way operation. Expiry cannot be renewed by mutating an old record. Reapproval needs a new reviewed record, without resetting any one-time claim.

Only the server derives `sessionTokenHash` from the actual HttpOnly Secure session cookie. Never accept a digest, actor ID, role or active organization asserted by browser JSON/headers. This branch adds no HTTP publication route and changes no CSRF/cookie enforcement. `preparePublication` forwards its private server context to storage, then strips it from the returned prepared intent. Prepared means a local one-time intent, not published, dispatched or successful remotely.

`MySQLPublicationClaimStore` retains org-budget → website → content → existing claim → content policy → legacy health → reservation locking. The new boundary then locks current session/user, authorization, durable approve event, both memberships/users, policy revision, destination, attestation and issuer state. Claim insert, authorization consume CAS, authorization-use audit, content event and `publication_unknown` CAS commit in the **same transaction**. Legacy unsigned health may deny but cannot grant: fresh valid signed evidence with `publish` capability and matching destination is also mandatory. No trusted issuer means deny. Missing new tables/rows means deny, with rollback; no compatibility fallback exists.

HMAC-SHA256 is implemented for the injected trusted connector-probe boundary, with >=32-byte synthetic keys in tests only. Evidence canonicalization has a fixed tuple; issuer/key/revision, org/site/channel, destination/revision/target, status, capabilities and checked/expiry are covered. Current issuer revocation/revision is read under lock every time. Unknown/disconnected/unavailable, read-only, forged, stale, revoked or wrong-scope evidence cannot authorize publication. A fresh health attestation can legitimately serve multiple distinct approved contents for that destination; it is not itself a single-use publication token. The current reader verifies the envelope each time; a durable ingestion/history writer and anti-rebinding constraints remain required.

All writers touching these records must honor compatible lock ordering. Row locks serialize claim vs cancellation, policy/feature disable, session revocation and membership changes at the transaction boundary; they do not promise revocation of an already committed remote dispatch. This branch performs no dispatch. Real MariaDB deadlocks, isolation level, phantom/gap locks and timeout behavior must be independently tested. On a deadlock or unknown commit outcome, reconcile/re-read the same unique claim identity; never retry a provider action or clear a claim. An `absent` provider result remains terminal and does not grant another attempt.

Preserve signed provider observation verification, observation replay journal, monotonic terminal claim states and atomic reconciliation. The existing provider-observation envelope binds a unique claim identity rather than an explicit destination field; the future real probe must resolve the claim's immutable authorization/destination and attest the correct account. No live provider attestation or full destination-aware outbound adapter is certified by this work. Generation reservation completion is not a new publication quota or permission to incur another provider charge; chargeable publishing budget/quota integration remains a separate gate.
